# 相关项目对照

本文件记录与 DFS 定位相近或易被混淆的公开项目，说明差异点，供选型与对外说明使用。

> 说明：以下为生态观察与公开资料整理，非严格评测；各项目演进较快，差异点以「机制」而非「功能列表」为准。

## 1. SkillRun（`.skr` 制品）

- **输入**：`SKILL.md` + 配套代码 + 契约
- **机制**：打包成制品，由 Skill runtime 加载；契约（manifest）锁定 IO、权限、模型绑定；介质不匹配即失败
- **性质**：**Skill Capsule 路线**——Skill 合约静态固化，直接解释执行
- **与 DFS 关系**：对照项。DFS 在它之上增加「编译期由模型生成计划」这一步，因而不是固定合约，而是「规约 → 计划」

## 2. Skillscript

- **输入**：声明式 Skill 源码
- **机制**：自带 runtime + CLI + MCP 服务，支持权限审计与人工审批节点
- **性质**：Skill 本身就是可执行源码，runtime 是解释器
- **与 DFS 关系**：无编译期转化；流程写死在 Skill 定义里。DFS 的流程由模型在编译期生成

## 3. SkillFlow

- **输入**：自然语言
- **机制**：模型生成 DAG 工作流后执行，支持 MCP、人工卡点、审计日志
- **性质**：「自然语言 → 工作流」
- **与 DFS 关系**：输入源不同。DFS 要求标准化 Skill 规约作为输入，生成结果受契约约束、可 review、可入库

## 4. GitHub Agentic Workflows（gh-aw）

- **输入**：Markdown 描述
- **机制**：编译为 GitHub Actions YAML，在 CI 中运行
- **性质**：确定性转译 + 领域限定（CI/CD）
- **与 DFS 关系**：同为「编译」思路，但转译目标是流水线配置而非 LLM 运行计划；不涉及模型绑定与运行时推理

## 5. skillify

- **输入**：对话历史
- **机制**：提炼生成 `SKILL.md` + 脚本
- **性质**：反向——从经验生成 Skill
- **与 DFS 关系**：方向相反。skillify 可作为 DFS 的上游供给（把沉淀的经验变成规约）

## 6. Claude Code / Claw 生态的 SKILL.md 项目

- **输入**：`SKILL.md`
- **机制**：Agent 宿主按需加载，模型在对话中执行
- **性质**：Skill 是插件，宿主是 Agent
- **与 DFS 关系**：DFS 正是对这类模式的修正：把 Skill 从插件提升为应用的主结构

## 7. BMAD / Spec-Kit 类 spec 驱动开发

- **输入**：需求 spec（自然语言文档）
- **机制**：spec → 计划 → 任务 → 代码，偏向软件交付流程
- **性质**：spec 是需求文档，没有 Skill 契约体系
- **与 DFS 关系**：思想同源（规约先行、产物可 review），领域不同

---

## 差异矩阵

| 维度 | DFS | Skill Capsule | Skill 即源码 | NL→Workflow |
| --- | --- | --- | --- | --- |
| 输入是标准规约 | ✅ | ✅ | ✅ | ❌ |
| 存在编译期 | ✅ | ❌ | ❌ | 部分 |
| 模型参与生成流程 | ✅（编译期一次） | ❌ | ❌ | ✅（每次） |
| 流程可静态 review | ✅（`plan.json` 入库） | ✅ | ✅ | 弱 |
| 运行期无调度自由度 | ✅ | ✅ | ✅ | ✅ |
| 规约变更需重新编译 | ✅ | 需重新打包 | 否 | 不适用 |

## 结论

在公开生态中，**「以 Skill 规约为输入、由模型在编译期生成运行计划、运行期按计划确定性执行」这一组合形态尚无同名同构项目**。DFS 的差异化点集中在两处：

1. 编译期与运行期职责分离，模型自由度只出现在前者；
2. 编译产物（`plan.json`）是一等制品，可入库、可 review、可版本对比。
