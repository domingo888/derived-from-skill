# 设计动因：为什么需要 Derived From Skill

本文把 README 的动因部分展开为可论证的结构，供设计评审、架构决策记录（ADR）与对外说明使用。

---

## 1. Skill 的原始设计意图

Skill 出现的技术动机有三层：

1. **收敛推理范围**：把「一类任务该怎么做」写死在规约里，模型不必从零推导步骤。
2. **降低 Token 开销**：流程不必每轮由模型重新生成，上下文只需承载当前任务的数据。
3. **稳定复现**：同一类任务、同一份规约，产出结构与质量应可预期。

这三层收益成立的前提是：**执行路径由规约决定，而非每轮由调度层重新决定**。

---

## 2. 宿主架构如何侵蚀这三点

### 2.1 收益一被路由覆盖

当宿主注册 N 个 Skill，模型在每轮都要额外完成一次「选哪个」的判断。这个判断的成本与 N、以及 Skill 间语义重叠度正相关，并且它是**没有规约约束的自由推理**——正是 Skill 想消除的那类推理。

### 2.2 收益二被引导成本抵消

规约写得再细，也要先被正确触发。触发依赖用户的表达与 Skill 描述的匹配度。匹配失败时，纠偏轮次产生的 Token 往往超过 Skill 节省的 Token。

设单任务自由推理成本 $C_f$，规约执行成本 $C_s$（$C_s \ll C_f$），纠偏期望轮次 $E[r]$ 与单轮成本 $C_r$：

$$C_{total} = C_s + E[r] \cdot C_r$$

当 $E[r] \cdot C_r > C_f - C_s$ 时，使用 Skill 反而更贵。多 Skill 场景下 $E[r]$ 随 N 上升，因此「Skill 越多越省」并不成立，存在一个效率拐点。

### 2.3 收益三被上下文漂移破坏

对话上下文中，历史内容持续参与后续推理。在单 Skill 场景中这是「上下文记忆」，在多 Skill 场景中则变成「历史吸附」：早前讨论过的 Skill 会持续吸引后续请求，即使当前请求属于另一个 Skill 的领域。

---

## 3. 结构诊断：自由度不守恒

把系统看成两个组件：

- **Agent**：高自由度、低确定性。其职责是「在开放空间里选择与规划」。
- **Skill**：低自由度、高确定性。其职责是「在封闭路径里稳定执行」。

挂载关系构成一个串联系统，其整体确定性由最不确定的环节决定：

$$D_{system} = \min(D_{agent}, D_{skill}) = D_{agent}$

也就是说，**只要 Agent 的调度自由度还在链路中，Skill 的确定性就无法传导到结果**。加大 Skill 规约的严格程度、优化 Skill 描述文案，都只能改善 $D_{skill}$，而 $D_{agent}$ 不变，因此系统确定性不变。

这是架构问题，不是提示词问题。

---

## 4. 可能的解法与其代价

| 解法 | 做法 | 代价 |
| --- | --- | --- |
| A. 强化提示词约束 | 在系统提示里严令「只能用某个 Skill」 | 概率性，仍属自由推理；换模型/换版本即失效 |
| B. 单 Skill 宿主 | 一个 Agent 只装一个 Skill | 部署单元翻倍，且运行时仍存在开放式会话循环 |
| C. 静态打包（Capsule） | 把流程固化成可执行合约 | 完全失去规约内的柔性，流程微调需重新打包 |
| D. **DFS（本项目）** | 规约 → 编译期由模型生成计划 → 运行期确定性执行 | 多一道编译工序；制品数量增长 |

DFS 选择 D：**在编译期一次性消耗模型的自由度，在运行期不再保留它。**

---

## 5. 自由度的搬迁，而非消灭

DFS 不是「让模型少思考」，而是**把模型的思考从运行期搬到编译期**：

| 阶段 | 模型做什么 | 为什么放在这里 |
| --- | --- | --- |
| 编译期（一次） | 理解 Skill 意图、拆解步骤、设计分支、生成提示模板 | 这里是「理解与设计」问题，需要模型的语义能力；且只发生一次，成本可摊销 |
| 运行期（每次） | 在已定步骤内做参数解析、内容生成、分支选择 | 这里是「执行」问题，只需节点内推理，不需要规划 |

由此得到两个性质：

1. **运行成本与次数线性相关，与任务复杂度弱相关**——因为复杂度已在编译期吸收。
2. **失败可定位**：失败要么在编译期（计划不合契约，可静态检出），要么在运行期某个具体步骤（有证据链），不会出现「说不清哪里错了」的模糊失败。

---

## 6. 对 Skill 质量的要求并未降低，只是改变了暴露方式

DFS 不宣称「Skill 写得糙也能跑好」。它改变的是**缺陷暴露的位置**：

- Agent 模式下，Skill 描述含糊 → 表现为偶发选错、偶发偏题，难以复现、难以测试；
- DFS 模式下，Skill 规约含糊 → 表现为编译失败或计划不合契约，**可被 lint 与 CI 挡住**。

把偶发的运行时故障，转成确定性的构建期失败，是 DFS 在工程上的主要价值主张。

---

## 7. 结论

1. 多 Skill Agent 的失稳不是提示词缺陷，而是「高自由度调度器串联高确定性执行单元」这一拓扑导致的结构性问题。
2. 该问题在运行时无解，只能通过**移除运行期的调度自由度**解决。
3. DFS 通过「规约 → 编译 → 计划 → 执行」的四段结构，把自由度集中到编译期，使运行期成为确定性执行。
4. 因此 DFS 的定位不是「更好的 Agent」，而是「**把 Skill 变成应用的编译范式**」。
