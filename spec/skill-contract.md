# Skill 规约书写约定

DFS 的输入是 Skill 规约。规约质量直接决定编译出的计划质量。本文给出必须满足的最低要求与推荐写法。

## 1. 必须包含的要素

| 要素 | 说明 | 缺失后果 |
| --- | --- | --- |
| 任务目标 | 一句话说明「这把活干什么」，含明确动词 | 编译出的计划方向漂移 |
| 输入定义 | 每个字段的名称、类型、是否必填、取值范围 | 与 `io.input_schema` 不一致，运行时校验失败 |
| 输出定义 | 每个字段的名称、类型、结构约束 | 与 `io.output_schema` 不一致，输出校验失败 |
| 流程步骤 | 有序步骤，每步一个明确动作 | 模型只能凭猜测编排，计划不可复现 |
| 边界与非目标 | 明确不处理什么 | 计划越界，触发规约外行为 |
| 失败处理 | 缺数据、格式错、超范围时怎么办 | 运行时随机中止或产出脏结果 |

## 2. 推荐写法

### 2.1 用可验证的表述替代形容词

| 差 | 好 |
| --- | --- |
| 「输出要专业、准确」 | 「输出必须包含 `invoice_no`，且长度为 8–20 位字母数字」 |
| 「合理拆分步骤」 | 「步骤 1 抽取字段；步骤 2 校验金额合计；步骤 3 生成对账结论」 |
| 「注意异常情况」 | 「金额为空时输出 `status:"missing_amount"` 并跳过步骤 3」 |

### 2.2 一步一个动作

一个步骤只做一件事。把「抽取并校验并汇总」拆成三步，因为：

- 单步失败可定位；
- 编译出的计划更短、更稳定；
- 便于在 `plan.json` 里 review。

### 2.3 显式声明不可逆动作

涉及写入、发送、删除的步骤必须在规约中标注，并在 `dfs.json.tools` 中按需开白名单。默认不允许。

### 2.4 输入输出与 schema 一一对应

`SKILL.md` 中的输入输出描述，必须与 `dfs.json.io` 的 JSON Schema 逐字段对齐。运行时以 schema 为准，文档不一致属于规约缺陷。

## 3. 示例骨架

```markdown
# <Skill 名称>

## 目标
<一句话，含明确动词与产出物>

## 输入
- `field_a`（string，必填，1–40 字）：<含义>
- `field_b`（number，可选）：<含义，默认值>

## 输出
- `result_x`（string）：<含义与格式约束>
- `status`（string，枚举：ok / missing_amount / invalid）：<含义>

## 流程
1. <动作一>：从输入取得 ……，产出 ……
2. <动作二>：基于 …… 校验 ……，不通过则转步骤 4
3. <动作三>：汇总并生成 ……
4. <异常出口>：输出 status 并结束

## 边界
- 不处理 ……
- 超过 …… 的数据直接返回 `status:"invalid"`

## 失败处理
- 输入缺 `field_a` → 直接失败（schema 层拦截）
- 金额合计偏差 > 0.01 → `status:"missing_amount"`
```

## 4. 与 DFS 编译的关系

- 规约里的「流程」是**意图描述**，不是最终执行 DAG；编译期模型会把它转成可执行步骤；
- 规约里的「边界」会被转成 `check` 步骤与输出校验；
- 规约里的「失败处理」会被转成计划中的异常出口，运行时按 fail closed 执行。

因此：**规约写得越可验证，编译产物越接近人工设计的流程；写得越含糊，编译期的自由度越大，可复现性越差。**
